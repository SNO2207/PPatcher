# Counterfeit-warning dialog

In Parallels Desktop 27.0.3 (58680) for ARM64, the blocking dialog headed “This copy of Parallels Desktop may not be genuine” corresponds to SDK error `0xFFFFD4B9` (`-11079`). The SDK's error-message table associates that code with the screenshot's title and detailed counterfeit warning. The client maps the same code to its sole “Get Genuine Copy” button.

IDA shows that the client receives this as a `CMessageInfo` result. Its virtual `isMessageShouldBeSkipped` method at `0x1001F1DF8` already suppresses two unrelated result codes (`-34004` and `-34001`) and otherwise delegates to the shared GUI filter. The button-response handler separately checks `-11079` at `0x1001F3804` and launches the vendor link. Neither that handler nor the message table identifies the upstream detector. In the client, dispatcher, and VM executable databases reviewed here, no local producer of literal `-11079` was found. It may arrive in a license event from another component or a service response; that source remains unproven.

The PoC adds an early `-11079` comparison to the client's existing skip method. Its entry branches to an unused executable header region at `0x100002000`. The helper reads `CMessageInfo::data()->result`; for `-11079` it returns true (skip). For every other code it replays the displaced prologue and returns to `0x1001F1DFC`, preserving the original filter. The patch changes the first four bytes at the method entry and writes 36 bytes in the checked, previously zero-filled header region. The one-file builder verifies the reviewed instruction anchor and empty region before patching, then re-signs and validates the bundle.

On 21 October 2026, the locally installed build passed `codesign --verify --deep --strict`. The `Premium Linked Clone PoC` started through Control Center, remained running without the counterfeit modal appearing in the client window, and passed guest DNS and two HTTPS checks (`HTTP 200`, TLS verification success). This is one boot observation; it does not establish whether the same status will recur after a later license heartbeat.

## Upstream investigation (21 October 2026)

IDA searches for an instruction constructing `-11079` (the full 32-bit value, its low halfword, and the complement used by an ARM64 `MOVN`) found no producer in the dispatcher, VM executable, SDK communication library, abstract-task library, or the other Parallels frameworks inspected. The SDK contains the error-to-message table; the client has two comparisons used for the button and its response. Each executable also has an error-name mapping for `PRL_ERR_TRIGGERED`. An error-name mapping alone does not create the event. This narrows the search but cannot exclude arithmetic construction, encoded data, or a status loaded from a service response.

The dispatcher does have a concrete identity check: `sub_100576FF8` asks macOS for its client's audit token and verifies signing identifier `com.parallels.desktop.console` and Parallels' Team ID through `sub_100554C30`/`sub_100554DAC`. Its only observed caller is `sub_1002F3E04`, a TPM-syncing task. The runtime log's “Wrong type of client. This task can work with genuine GUI of PD only” comes from that caller and returns a separate failure status. The VM executable has a reciprocal dispatcher peer check in `sub_10004BDBC`. These checks are real, but the available call graph does not connect them to the counterfeit modal; patching the TPM gate would therefore be an unvalidated change for this issue. The dispatcher also collects GUI and dispatcher signing results for problem reports in `sub_100117048`; that path is diagnostic evidence, not an identified warning producer.

The host log records the counterfeit message under the VM's UUID after VM start, but has no licensing network request immediately before that particular message. This does not prove the result is local: a previous response or delayed event could still supply it. An LLDB breakpoint on the suppressed client's `-11079` path did not fire during the short observation window, so no live caller stack was captured. A proposed VM suspend/resume trace could not run because `prlctl suspend` itself rejected the command as Pro/Business-only; the running VM was left untouched.

The current PoC filters the modal when this result reaches the client. It does not make the copy genuine or establish an upstream detector or bypass. An upstream patch should wait for a captured producer path and a before/after runtime test tied to that path.
